# Gallery 展示与维护

## 展示顺序

首页先展示“能产出什么”，再解释过程。每项使用一张代表作、一句用途、输入输出、依赖和安装入口。截图或成品比功能标签更能帮助读者判断是否适合自己。

详情页按以下顺序组织：

1. 真实请求与产物预览。
2. 适用任务、输入要求和明确不覆盖的任务。
3. 可复制的调用示例与安装目录。
4. 工具依赖、验证范围和已知缺口。
5. SKILL.md 及可按需阅读的参考文件。

避免大段重复口号、无依据的成功率、未经测量的节省时间与空分类。每个预览说明实际来源；概念插画不冒充运行截图。

## 信息结构

- 一个 skill 一个目录，稳定 ID 与文件夹名一致。
- 分类描述任务，标签描述具体场景。不要把模型名当作主要分类。
- `catalog.json` 保存展示元数据；工作指令只维护在 `skills/`，详情页不另复制一套规则。
- `examples/` 保存经过筛选的公开产物和请求，不放完整运行缓存。
- 公共说明与个人配置分开。二维码、绝对路径、私有资料、账号凭据和默认发布目标不进入通用 skill。

## 版本与验证

当前版本在 catalog.json 中维护。变更行为时更新版本，Git 历史保留差异。多人使用后，重要版本可加 Git 标签与 Release，避免安装时不清楚规则变更。

区分三种状态：结构校验、真实任务使用、在干净环境复现。不要用“已测试”同时代指三者。新增依赖或权限要求也应记录。

## 后续网页

技能数量增加后，可以用同一份 catalog.json 构建静态 Gallery：按分类筛选、关键词搜索、查看案例、复制安装请求。第一版无需账号、数据库或复杂后台。若需要打包分发到应用内，再按目标平台规范增加插件清单；不把仓库公开等同于插件市场上架。
