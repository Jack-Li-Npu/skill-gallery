# 案例取材与配图

## 官方示例优先

体验顺序为：查找官方推荐示例 → 按原步骤运行并检查真实结果 → 没有合适示例时自行设计任务。优先查看 README、Quickstart、examples/demo 目录、随附样例数据和官方在线演示。说明书里的成功路径应先于随手设计的小工具，避免案例只覆盖自己熟悉的功能而掩盖项目特色。

示例围绕项目的核心卖点选择。设计工具应展示字体、图像、布局、交互或内容组织上的实质差异，必要时试多个官方样例；只改颜色或做一个通用后台不能代表它的审美范围。其他项目按其功能选择代表性输入和输出，不固定示例数量。

区分“运行仓库自带页面”“按官方提示重新生成”“自拟任务”，记录来源、步骤、实际执行范围和结果。官方成品不能写成本次新生成；静态示例里的预订、支付或模型输出界面不能证明后台能力。遇到示例缺失、过时、设备不符或额外授权依赖时，记录原因，采用可行的官方路径或自拟案例，不伪称复现成功。官方示例已充分说明能力时，不强加自拟案例；需要体现结果复用时可补充。

官方示例与下面的外部社区案例是两项独立要求，不能互相替代。

## 任务价值

选读者有动机使用的任务：批量处理、持续更新、组合环节或产出可用成品。避免只抓随手可读的网页、展示教学站点，或把“打开应用”当作全部体验。具体说明项目承担哪部分工作，不虚构不可替代性。

记录输入、配置、操作、输出，核对内容完整性。语音检查末句和选定音色；抓取检查字段、覆盖范围与导出结果。HTTP 200、进度完成或文件存在不代表满足要求。模型依赖可用、权重齐全和参数生效分开确认。

必要修补保留小补丁、适用版本和复现步骤。正文说明影响使用的差异即可。本机硬件与模型对应本次测量，不成为所有引擎的门槛或承诺。

## 社区案例

社区检索是每篇完整项目文章的硬性要求，不等用户再次提醒。实际搜索 X、Reddit、开源社区或开发者网站，打开原始帖子、采用记录或应用仓库核实。至少加入一个包含具体任务、操作和结果素材的外部使用案例。本机自测、官方模板、README 展示及设想用途不能替代此项；官方案例索引可以作为寻找原始使用记录的入口。只调整既有图片或排版时不必重做整轮检索。

内部保存检索词、日期、查阅结果、未采用原因和案例到素材的对应关系。先检查确实使用了被评项目，再检查原始结果，排除同名产品、泛泛推荐和转发。原帖不可读时，可以核对其关联的公开提交、应用仓库或演示；仅有搜索摘要时不声称已经读过原文。

找不到可核实案例时，继续检查公开采用记录、项目讨论和关联提交。仍无可用素材则明确报告这一项未完成，保留调研记录，不编造博主测试、不把官方演示改写为社区实测，也不宣称全部交付要求已满足。

候选素材应尽量包含：任务与设备／输入，具体操作或配置，实际结果截图／音频／视频片段／成品，以及保存在内部的作者、原帖、时间与素材对应关系。

优先选有真实素材的案例。只有“克隆成功”的一句话不能撑起图文案例；保留其自述时，另外展示的官方样音必须说明真实身份。不用评论截图或一句引语代替结果。

逐段核对视频。仓库首页、官方样音、安装过程和博主本人的成品分别处理，不能凭标题判断画面性质。只有公开源码时可以运行界面补图，简短注明为该应用源码画面；内置故事和示例数据不能冒充新生成结果。

正文自然写“也有博主用……测试”“有开发者把……接到……”，不点名平台、账号、社区、姓名或原帖链接。内部保留追溯信息。用自己的语言概述事实，遵守素材使用条件，不整段搬运他人文章。需要公开署名或许可声明的素材，在随稿出处文件或许可允许的位置保留；若与用户发布格式冲突，改用允许该形式的素材，不用内部证据替代必须公开的署名。保留影响选型的负面反馈，如设置复杂、输出截断、平台限制。

## 先成文，再设计首图与封面

生成顺序是：核实资料与结果 → 写完整的项目介绍 → 确认文章标题 → 提取画面信息 → 编写有上下文的提示词 → 生成并检查。这里调整的是制作顺序，正文首图仍放在文章开头；不据此交换文章内图片位置。修改既有配图时，先读当前正文和证据，从已有介绍提取内容。

配图前保存一份内部视觉简报，包含介绍原文、目标读者的具体处境与情绪、项目带来的实际帮助、核心机制、输入输出、典型任务，以及可以展示的实测或社区结果。先让读者从画面认出熟悉的处境，再呈现项目能接走的工作和产物。不要把每张首图都画成组件流程图；桌面场景、人物反应、梗图拼贴也能表达具体用途。

用户提供的表情图可作为画面中的调侃元素，保留人物表情和关键文案，以贴纸、剪贴或局部画格融入构图。它承担共鸣，项目产物承担功能说明，标题仍是最醒目的文字。不要仅换标题、让原来的通用产品示意继续占据全部画面，也不要用梗图代替实测结果或伪造项目界面。金融类画面可表达看盘受挫和复盘疲惫，不能暗示使用工具后必然转亏为盈。

提示词同时提供介绍原文和精简后的画面信息，明确哪些只是理解背景、哪些文字必须准确出现在图中。可用以下骨架，按项目删改：

```text
用途与尺寸：正文首图 / 消息列表宽封面 / 方封面；实际宽高比。
文章标题：完整准确的中文标题，作为最醒目的文字。
介绍原文：[已完成的概览段落，供理解项目，不要求全部排进图中]。
读者共鸣：[具体处境、情绪、熟悉的表达，以及可使用的用户梗图；不强加焦虑]。
实际帮助：[项目能减少哪段工作、交付什么结果；与情绪共鸣明确接上]。
事实与结果：[核心组件、输入输出、使用场景、核实过的结果；数字附适用条件]。
画面叙事：[读者从主体、流程、局部细节或前后状态中能看懂什么]。
上图文字：[标题及必要的短标签；事实来自上面的正文与证据]。
设计方向：[适合该项目的视觉风格、配色、构图和信息层级]。
层级与留边：标题优先，其次主体与核心关系，最后辅助细节；缩略图仍能读清标题。
```

正文首图可以用场景、流程、局部放大、结果卡片或前后状态增加信息量。细节围绕同一条解释路径组织，不把介绍整段缩成小字，也不为凑满画面添加未经验证的能力或数字。具体性能结果保留影响理解的测试条件；概念示意与真实截图分开。

风格和布局每篇可以不同，按项目内容与读者任务选择，例如编辑式信息图、产品场景剖面、工作台全景、漫画拼贴或流程叙事；不再固定深色科技背景、左右分栏和底部参数格。参考最近作品，避免机械复用构图，不为求不同牺牲清晰度。检查缩略图中标题是否可读、情绪切入是否能被看懂、项目用途是否具体，三者兼顾。技术架构图继续使用下方约定的英文手绘样式，除非用户另有要求。

## 图像分工

| 图像 | 默认样式 | 内容要求 |
| --- | --- | --- |
| 正文首图 | 中文大标题；风格、配色与布局按项目选择 | 标题与正文一致；结合介绍展开机制、场景与有依据的结果，信息比缩略封面丰富；概念插画不能冒充实际界面 |
| 公众号宽版与方版封面 | 分别构图，突出同题中文标题与主要视觉 | 从正文首图的视觉简报选取核心信息，保留缩略图可读性，不机械塞入全部细节 |
| 技术架构图 | 全英文、白底手绘、蓝色组件与虚线分组、绿色模型、橙色输入、黑色箭头 | 不加整体标题或副标题；项目名可作分组标识；表达真实组件与数据流 |
| 运行和案例截图 | 实际产品或原演示画面 | 展示输入、操作、参数或结果，文字解释图中值得看的内容 |

封面借助构图和中文排版形成吸引力，不堆无关数字、品牌或话术。参考图只用于风格，不复制其他领域事实。用本次测量时带上关键硬件／模型条件。

区分正文首图与公众号封面。后续文章的正文首图默认采用 16:9，例如 1600×900；公众号封面同时提供两张：约 2.35:1 的消息列表宽版，以及 1:1 的转发卡片／公众号主页方版。可用 1880×800 作宽版构图起点，仍以当前发布后台的实际裁切预览为准，不能把 16:9 当作消息列表封面框的比例。

宽版和方版分别重新安排标题与主体，不直接从正文首图或宽版裁掉文字来生成另一种比例。三种图使用同一份已核实的内容简报，分别按比例选取细节；正文首图承载更完整的解释，公众号封面保留醒目中文标题和主要信息。标题、项目标识和关键视觉留出边缘安全区。检查实际宽框裁切后文字与主体完整、缩略图可读。用户只更新工作流或说明“下次”时，不据此重做当前已认可图片。

架构图标签用简短英文，给较长术语留空间。单向流程与双向调用／返回分开，箭头起止明确，不悬空、穿过文字或连接错误模块。删除标题区后重排图形，不留大块空白。不用“发现、安装、测试、写作”的制作过程替代产品架构。

生成／编辑栅格图时使用可用的 imagegen 技能和内置工具。明确参考图角色、精确文字、保留项与修改范围；检查生成文字、数字、箭头、语言及其与正文的对应关系，确认画面确实解释了标题以外的信息。介绍或结果改变时复核图片是否仍准确。已认可封面不因另一张图的修改重做。最终资产放项目目录，介绍依据、视觉简报、实际提示词与制作记录放内部证据。

截图移除私人标签、书签、令牌与无关区域，不改造截图来制造结果。遵守截图／浏览器工具的访问范围；被拒绝时不换路径绕过。
